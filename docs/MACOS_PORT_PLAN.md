# macOS port plan

Status: proposal, 28 October 2026. Based on `origin/main` at `b6fbd94c`. The first Metal bring-up is in progress in this task worktree. The macOS workspace check and dev build succeeded, and the offline demo initialized Metal and produced an inspected screenshot after fixing hidden-window startup. Broader visual comparison and validation remain open. No grid test or release validation has been performed.

## Goal and scope

Produce a macOS viewer with the same visible behaviour and protocol as the existing viewer, without regressing Windows or Linux. Start feasibility testing on Apple silicon; decide the minimum macOS version and whether to support Intel Macs after measuring actual hardware, dependencies and distribution constraints. The first milestone is a working local demo, not a claim of feature parity or release readiness. Human validation is required before a viewer-changing PR; only the human connects to a grid or handles credentials.

## Rendering options

| Route | Assessment | Decision |
|---|---|---|
| wgpu Metal backend | wgpu already sits between Aurora and the GPU and provides a native Metal backend on macOS. WGSL remains the shared shader input. Vulkan-specific code and feature assumptions still need work. | First feasibility candidate; not yet proven compatible or faster. |
| wgpu Vulkan via MoltenVK | Retains the Vulkan API path but maps a Vulkan subset to Metal. wgpu requires its `vulkan-portability` feature on Apple platforms; runtime integration, portability and the existing direct Vulkan code must be checked. | Comparison or fallback if Metal proves unsuitable; no assumption of feature or performance equivalence. |
| Direct Metal renderer | Uses Apple's graphics API directly, but entails a separate renderer, shader and resource management path, and ongoing parity work. | Consider only if a measured, material limitation cannot be addressed through wgpu. |
| wgpu GLES via ANGLE | wgpu documents ANGLE as an optional macOS backend. Compatibility with Aurora's compute, binding arrays and indirect rendering is unproven and may require substantial redesign. | Research fallback only; probe requirements before considering it. |

macOS does not have a native Vulkan driver according to the MoltenVK project. Both the native wgpu Metal route and direct Metal avoid MoltenVK; neither removes the need to test hardware capabilities. Benchmark comparable scenes and settings before selecting a backend: no performance ranking is established here.

Sources checked 28 October 2026: [wgpu backend and shader features](https://wgpu.rs/doc/wgpu/documentation/features/index.html), [wgpu 30.0.1 feature capabilities](https://docs.rs/wgpu/30.0.1/wgpu/struct.Features.html), [MoltenVK design and limitations](https://github.com/KhronosGroup/MoltenVK), [Apple Metal documentation](https://developer.apple.com/documentation/metal).

## Starting points on the unmodified base

- `crates/aurora-render/src/main_thread.rs` selects and enumerates Vulkan explicitly. `open_device` requires texture binding arrays, non-uniform indexing, at least 64 array elements, and `INDIRECT_FIRST_INSTANCE`; support must be measured on each candidate backend and GPU.
- `dedicated.rs`, `vram.rs` and `main_thread.rs` access Vulkan HAL or use `ash`. Audit compilation and behaviour on Metal, with safe alternatives for allocation and memory accounting. Check indirect draw fallbacks, texture compression, depth clipping, timestamps and visual equivalence; some are already optional, not necessarily equivalent in practice.
- `crates/aurora-updater/src/media_pack.rs` treats every non-Linux target as Windows and selects Windows binaries. Prevent an incorrect download and audit plugin paths, shared memory, process launch and media keys before enabling media on macOS. A working macOS media pack is not established.
- The release and media workflows target Windows and Linux; updater installation has Windows-only paths. The existing macOS task and font lists are unvalidated. Inventory platform-specific code and native dependencies before estimating completion.

## Feasibility findings (28 October 2026)

On the investigated Mac, macOS 15.7.7 reports an Apple M2 Pro GPU. A native Metal probe found Apple7 and Mac2 families and Argument Buffers Tier 2; its recommended maximum working set was 22,906,503,168 bytes. These are Metal device properties; the separate viewer initialization result is recorded below.

The wgpu 30.0.1 Metal adapter source enables texture binding arrays and non-uniform indexing when MSL 3.0, texture arrays and Tier 2 argument buffers are available. Tier 2 also gives a binding-array limit of 1,000,000 in that source. The measured Tier 2 is encouraging, but the full conditions, actual wgpu-reported features and limits, device creation and shaders must be checked on this machine. `INDIRECT_FIRST_INSTANCE` is documented on Metal Apple3+ or Mac1+; the device reports Apple7 and Mac2. The later demo opened the device with Aurora’s required features, but this does not establish correct rendering.

A concrete performance limitation needs its own milestone: wgpu 30.0.1 documents `MULTI_DRAW_INDIRECT_COUNT` for Vulkan and DX12, not Metal. Aurora's `GpuCull::supported` selects its CPU-built draw lists when that feature is absent (`main_thread.rs`); that fallback is a first bring-up route, not evidence of equivalent performance or visuals. Measure it on representative scenes. Investigate a GPU-driven alternative, including whether it can be expressed with wgpu or requires backend-specific integration, without assuming either approach is feasible.

`dedicated.rs` already falls back to wgpu allocation when its Vulkan HAL access is unavailable. This is a runtime fallback, not proof that the Vulkan-specific references compile on a Metal-only build or that allocation and memory-pressure behaviour is acceptable. `vram.rs` and adapter VRAM detection also rely on Vulkan queries; assess a Metal-aware budget or a documented safe fallback for unified memory.

A baseline `cargo check --workspace --locked` was run on the plan's `b6fbd94c` worktree with Xcode 16.2 and Rust 1.99.1 (`aarch64-apple-darwin`). Dependencies downloaded and compiled, but `aurora-render` failed with six errors: `wgpu::hal::api::Vulkan` and `wgpu::hal::vulkan` are configured out for the default macOS Metal build. The references are in `dedicated.rs`, `vram.rs` and `main_thread.rs`. The Vulkan code must therefore be conditionally compiled, with working non-Vulkan implementations, before the workspace can compile. The check stopped there, so further errors may remain. This describes the unmodified baseline before the subsequent bring-up below.

Sources: [wgpu 30.0.1 Metal adapter](https://raw.githubusercontent.com/gfx-rs/wgpu/v30.0.1/wgpu-hal/src/metal/adapter.rs), [wgpu 30.0.1 features](https://docs.rs/wgpu/30.0.1/wgpu/struct.Features.html), [wgpu backend features](https://wgpu.rs/doc/wgpu/documentation/features/index.html).

## Bring-up results and repair plan (28 October 2026)

For the separate macOS Rust checks and the Windows-only PowerShell 5.1 gate,
see [Quality checks on macOS](TESTING.md#quality-checks-on-macos).

The task worktree selects Metal on macOS, compiles out Vulkan-only memory queries and dedicated allocations there, and prevents the viewer from fetching the Windows media pack. The macOS Vulkan-style memory-budget probe still returns no hard budget, and wgpu handles texture allocations. The texture-pressure target now also uses Metal’s recommended working set and current device resource allocations as advisory values, bounded by the texture setting. The recommendation is neither a hard allocation limit nor a measure of free memory. Windows and Linux still select Vulkan, but their builds and rendering have not been revalidated for this change.

On macOS 15.7.7 and Apple M2 Pro, `cargo check --workspace --locked` and the default dev viewer build succeeded. A separate offline demo launch logged `Apple M2 Pro (Metal)`, a ready renderer and CPU-built draw lists. A filtered workspace test of the unavailable media pack passed, and formatting and `git diff --check` passed. These results establish device initialization, not correct pixels, interaction, performance or grid support. The build reported linker warnings from bundled Intel texture-compression objects; their impact remains unverified.

The initial 620-frame and 30-frame demo attempts produced no capture and were stopped. The window was created hidden until its first presented frame, while wgpu Metal refuses to acquire a drawable from an occluded window. The frame profiler showed a running main loop with no draws. On macOS the window is now shown after renderer initialization so Metal can present its first frame. A fresh dev build ran the offline demo, presented a frame, saved the requested frame 620 and exited successfully. The screenshot was inspected: the demo scene, avatars and interface are visible. This is not a side-by-side fidelity or performance validation.

On the M2 Pro the Metal recommendation was 21,845 MiB, with 151 MiB allocated at the initial query. In the standard offline demo the texture target was 2,048 MiB; forcing a 512 MiB recommendation gave a 256 MiB target. In a separate 600-object streaming demo with the override, pressure rose when pages reached 349 MiB and returned to zero after they fell to 39 MiB (733 textures lowered). The filtered workspace texture-budget tests passed. The stress run was stopped after recording the pressure transition; its planned screenshot was not produced. These tests do not establish physical memory reclamation, system-wide pressure response, long-session stability, visual parity or a before/after performance comparison.

`cargo clippy --workspace --all-targets -- -D warnings` did not pass: pre-existing macOS unused-code warnings in unchanged viewer modules became errors. PowerShell is unavailable, so `check.ps1` could not run. A subsequent `cargo test --workspace` stopped in a GPU photo-look comparison: `Thematrix` exceeded its tolerance on Metal (280 passed, 1 failed, 18 ignored in the render crate); later test binaries did not run. A fresh workspace Clippy run with `-D warnings` still failed on existing unused-code warnings in unchanged macOS viewer modules. Filtered tests and demos do not replace the full checks.

On 28 October 2026 the human confirmed texture display and MOAP playback in the normal viewer. A later unfiltered `cargo test --workspace --locked --no-fail-fast` passed: 5,967 passed, 30 ignored. The portal round-trip test now allows floating-point rounding, the notecard test uses a cross-platform cursor shortcut, and the screen filter computes its rotation on the CPU as `LLImageFilter::filterScreen` does; the Metal comparison then passed. An offline Thematrix before/after capture was inspected on Apple silicon. macOS-only, item-scoped dead-code allowances identify existing Windows-specific code; they do not implement those platform features. The human confirmed the Thematrix before/after demo on 28 October 2026. Windows PowerShell 5.1 parsing and Windows CI remain outstanding.

For the reported media failures, macOS plugin path discovery recognizes a local `SLPlugin.app` bundle and native `.dylib` names; fixture tests cover that layout and preserve the existing search order. The existing media workflow's pinned Legacy Viewer sources and package versions built universal macOS SLPlugin, CEF / Dullahan and LibVLC binaries. The Xcode linker required a temporary correction to an unquoted exported-symbols path containing spaces. `scripts/package-macos-media.sh` assembles the resulting app bundle, CEF helpers, VLC modules and licences. On Apple silicon a local HTML snapshot rendered through the plugin, and the offline demo displayed an animated local page on a prim. This development bundle sits beside the local executable; no published macOS pack or automatic installation exists yet. A local muted H.264 video embedded in HTML produced a decoded frame and 91 content updates. The human confirmed MOAP playback in the normal viewer on 28 October 2026; interaction, audio and other video formats remain unverified. Parcel music uses the separate native audio stream: its local ICY receive/decode test passed, and the offline demo opened an audio output device, but neither confirms audible output or playback of an actual parcel stream.

An opt-in fixed-count Metal GPU culling experiment (`AURORA_METAL_GPU_CULL=1`) clears indirect argument slots before the compute pass and submits the current face-count upper bound; the wgpu Metal backend expands those into individual indirect draws. The existing Metal GPU test matched its CPU reference and, with argument buffers deliberately prefilled, verified unused slots were cleared. Filtered GPU-culling tests passed. CPU and experimental 600-object offline demos were then run sequentially with the same window size and the human keeping them visible. After loading, 16 / 15 one-second samples gave median frame times of 32.32 / 33.34 ms and render-thread frame times of 34.84 / 34.88 ms (CPU / experiment), with both near the 30 fps background cap. Both frame-900 screenshots were inspected; both runs exhausted texture pages and reported rejected uploads. These capped runs show no clear speedup and do not establish full visual parity or uncapped performance; repeat after resolving the texture limit with representative scenes. The renderer previously reported 79 texture pages on this Metal device because `open_device` applied the individual-texture limit to binding-array elements. Metal now uses the separate binding-array element limit, capped at 2,048 pages. A 600-object offline streaming demo loaded 600 textures at full resolution with 91 pages and no page-exhaustion warnings; frame 900 was captured and inspected. A filtered unit test covers the platform-specific limit. The human confirmed texture display in the normal viewer on 28 October 2026; broader visual parity remains unverified. The CPU path remains the default until regression and performance checks justify a change.

### Ordered work and acceptance criteria

1. **Capture and visibility — initial fix verified.** The 620-frame offline demo captured and exited after the Metal startup-window fix. The captured image was inspected. The human confirmed window display, resizing and restore after minimizing in the offline demo on 28 October 2026. Still verify occlusion and clean shutdown and compare visuals with the reference; these checks do not establish complete visual validation.
2. **Verify the Metal demo.** Capture the standard scene after the loading fade, resize and close it normally, and inspect objects, avatars, textures and interface. Compare relevant visuals with an equivalent existing viewer/Legacy Viewer scene and settings where available. Inspect validation logs; repeat after any fix. Exit: repeatable captures and no unexplained Metal validation errors, with differences and unavailable comparisons recorded.
3. **Make memory handling safe.** The initial Metal advisory threshold has been implemented and exercised in a short streaming demo. Measure the wgpu allocation fallback and behaviour under real system memory pressure and long sessions; refine the policy, respecting that Metal's recommended working set and actual allocation/pressure are different measures. Test budget changes, reclamation, and long sessions. Exit: a justified implementation or explicitly documented limitations, with measurements; do not treat the current unavailable probe as complete.
4. **Address performance.** Profile representative scenes and frame times with the CPU draw-list fallback. Investigate a GPU-driven Metal-compatible approach and measure candidates against that baseline without introducing a per-frame GPU wait. Record capabilities, resource limits, visual parity and costs; do not assume parity with Vulkan. Exit: measured results and a justified path, including any remaining limitation.
5. **Complete platform and quality gates.** Review macOS-specific warnings and linker messages, distinguishing pre-existing code from this task; coordinate fixes to unrelated code rather than changing another agent's work. Run the required workspace tests, formatting and Clippy, and `check.ps1` when its prerequisites and platform support are available. Verify that unavailable media is clearly reported without loading a Windows pack; investigate macOS media, voice and updater separately. Recheck Windows and Linux. Exit: required checks green or an explicitly recorded blocker, with no unsupported support claims.
6. **Human validation and release readiness.** Launch the test build for the human only after the automated demo and relevant checks are ready. Specify what to inspect and reserve any grid login and grid testing for the human. Complete the remaining platform, distribution, signing and release gates below before claiming macOS support. No PR for an unvalidated viewer change.

## Milestones and exit criteria

1. **Baseline and inventory.** Create an isolated task worktree based on current `origin/main`. Record macOS version, machine and GPU, Xcode tools, Rust toolchain and dependencies. Run the workspace build/check, classify compile and link failures, and inventory OS-specific paths. Do not modify another task's work. Consult the Legacy Viewer sources for relevant platform behaviour. Exit: reproducible build blockers and a prioritized inventory.
2. **GPU feasibility.** In the task worktree, enable the Metal backend and collect adapter features, limits and formats; check the exact requirements above and all direct Vulkan access. Run a minimal device/surface and shader test, then a representative demo. Record whether CPU draw-list fallback is selected, then separately investigate and measure a GPU-driven Metal alternative. If a required capability is absent, prototype a viable alternative with no visible regression and quantify its cost. Compare MoltenVK on the same machine and scenarios if it is a realistic candidate; document feature flags, loader/runtime packaging and limitations. Exit: measured compatibility, screenshots, validation errors, frame-time and memory results, and an evidence-based backend decision or a documented blocker.
3. **Working demo.** Fix compile/runtime portability, window lifecycle and resource paths. Exercise resizing, Retina scaling, multiple displays, keyboard shortcuts, Japanese IME, clipboard, file dialogs, fonts, audio output and clean shutdown. Capture screenshots of representative scenes and compare with the existing viewer and the Legacy Viewer under matching settings. Exit: repeatable demo scenarios with no known visual regressions; list anything deferred.
4. **Platform integrations.** Test Keychain-backed saved credentials without the agent accessing them, OS notifications, URL handling, permissions and microphone/audio devices. Investigate media plugins and voice independently, including build, architecture, licensing, bundle layout and runtime permissions; explicitly disable unavailable paths with a clear user-facing explanation. Review updates and data/cache paths, migration, sleep/wake and device changes. Grid-dependent tests remain for the human.
5. **Distribution and automation.** Add macOS CI for formatting, Clippy and workspace tests as feasible, plus actual GPU/demo validation on supported hardware. Design an `.app` bundle with correct resources, architecture, version and launch behaviour; decide archive/installer, signing, notarization and update policy before publication. Verify fresh install, upgrade, permissions and launch on supported macOS versions. Update build, testing and user documentation, including the generated wiki table when adding guides. Preserve Windows and Linux CI and tests.
6. **Release gate.** Run the project's required checks and relevant demo regressions; compare screenshots and profile representative scenes. Ask the human to validate the build and, where needed, log in and test networking, teleport, voice and media themselves. Record validated versions, hardware, results and remaining limitations; follow the repository's PR, review and merge rules. A release happens only when requested by the human.

## Decisions and open questions

- Which macOS versions and Intel GPUs are supported? Decide from capability probes, dependency support and available test hardware, not assumptions.
- Which media and voice capabilities are required for the first public build? Identify missing dependencies and agree on any visible limitations before release.
- How will signing, notarization, distribution and updates be provided? Verify the available Apple development setup and publication requirements before selecting a policy.
- Record exact test hardware, backend, feature/limit report, demo inputs, images and performance measurements. A successful build alone is not runtime or grid validation.
